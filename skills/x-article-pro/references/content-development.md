# 内容发展：先有值得读的材料，再把它写清楚

本文件用于新稿和实质改稿。维护 Skill 时不因此生成试稿；用户只改一句话时不扩大修改范围。句子级修改已有内容记录时只复核受影响内容并重新绑定；历史稿没有记录时不倒填虚构策划，只验本次文字修改，不称为新稿总验收。内容丰富度与句子自然度是两项工作：逐句通过的稿子，仍可能无聊、偏题或信息单薄。

## 研究全貌，再选主线

先读完整公告及其关键附件，列出这条新闻实际上包含哪些重要变化，再决定文章从哪里进入。不要先抓一个参数或一句口号，随后只搜索支持这个小角度的材料。

按事件相关性追问：发生了什么、相对什么改变、具体怎么发生或实现、谁在什么条件下能用、代价与局限是什么。演示/论文/产品更新有不同重点，不要求每篇凑齐固定维度，也不把清单照搬成正文小标题。

在内部记录中区分：准备写进正文的材料、帮助理解但不必写的背景、公开材料尚未回答的问题、与本篇无关的枝节。重要缺口先回到一手来源、配套文档、论文、演示或可比版本资料补查；记录查到什么和还缺什么。不是搜索摘要薄，就直接把长文章缩成短讯。

资料是否够用，以本篇承诺的问题能否被具体回答为准。没有更多可靠材料时，收窄承诺或如实保留未知，不填常识、不抄参数表、不为了“全面”堆无关背景。不设置统一字数、资料条数和观点次数。

## planning：实际使用 dbs-content

先运行依赖定位器的 `--stage planning --json`，读取返回的绝对 SKILL.md。把已确定的新闻、完整材料、读者问题和 X 长文章形式交给它；已有稿则直接做五维诊断，不重新询问选题或形式。

实际执行其内容组织、表达效率、认知落差与标题承诺诊断，并形成具体策划：

- 读者为什么会关心这件事；这是本篇读者假设，不是永久账号画像。
- 相比新闻摘要，正文多交付了什么具体理解、细节、判断或使用信息。
- 哪些材料最值得展开，如何从事实到解释推进；哪些缺口必须补，哪些枝节舍弃。
- 如果已有标题，它是否只靠夸张包装而缺少正文支撑。

策划结果写入 `content-review.json.planning`，交给 human-writing。它负责诊断，不代写全文；human-writing 仍是唯一主笔。不得用“已调用 dbs-content”或空泛“增强信息量”代替实际结论。

适配边界：不要求用户先有产品、付款链接或对标账号；不采用上游人物口头禅，不把其营销主张当已验证事实。已有图片和唯一封面工作流保持不变。上游的“不代写”只约束诊断阶段，不取消用户明确要求的后续成稿。

## 从资料变成阅读收获

- **案例与演示**：写出可观察的输入/条件、关键动作、结果及局限。过程公开了才写过程；只有成片就不脑补提示词、耗时、失败次数或用户亲测。图片承担展示事实的工作，正文补出图片看不出的背景与解释。
- **数据与对比**：说清数字测什么、和什么比、单位与条件。必要时算绝对变化，并解释能支持什么判断；百分点与相对百分比不混用。不同框架、硬件或数据集的分数不强作横比，榜单提升不直接等同真实任务提效。
- **机制与意义**：把发布方的说法、资料支持的解释和作者推断分开。意义要落在具体行为或判断变化上，不用“重新定义”“改变一切”替代论证。
- **实用信息**：入口、开放对象、版本、价格、地域、权限、前置条件等，只补会改变读者选择或行动的部分。不是每篇都硬加教程或商业结尾。
- **趣味来源**：优先找真实的异常结果、具体场景、前后差别、过程里的问题和有证据的意外。没有独家材料就不宣称独家；不靠假亲历、强行反转、身份对立或编造内幕制造兴趣。

“精炼”是删掉重复和无效包装，不是删掉必要的案例、解释、背景与事实限定。篇幅随信息展开；有价值的长段保留，短句多不等于内容密度高。

## review：实际使用 dbs-content-value

正文、标题、caption 有候选后，运行 `--stage review --json` 并读取返回的 SKILL.md；需要完整判断模型时读取其 diagnostic-model.md。默认模式 B，聚焦有没有阅读收获、是否持续推进、承诺是否兑现；没有商业目标不追问，不强行生成商业报告。

先只看读者最先接触的标题、caption 和开头，写出读者预计得到什么、谁有继续的理由。再阅读全文，用原句指出读者实际得到了什么、哪里开始重复/偏题、最有价值的内容是否被埋住。不能用后面的优点倒推开头一定有效，也不预测具体阅读量。

审查不能止于“增加案例、提升信息量”。每个内容问题写清原文证据、返回哪个阶段、实际采取什么动作以及修复后的落点：缺事实回研究，承诺与结构失配回策划/主笔，纯表达问题再交 humanizer-zh。禁止叠加多个主笔互相洗稿。

有实质修改时重新对照标题和 caption；轻编辑完成后再核对重要信息有没有被删薄。判断发现有未解决的核心问题，不标 reviewed。暂时无公开答案属于研究未知，不伪装为已解决事实；正文承诺必须与此相容。

## 内部记录与定稿绑定

每篇新稿使用一个内部 `content-review.json`，不进入公开 HTML、正文复制区或 caption。研究/策划阶段即可记录，最终绑定成稿；结构门槛不是兴趣评分，也不能证明 Agent 确实读了材料。实际执行记录与语义判断仍由编辑负责。

```text
python <skill目录>/scripts/validate_content.py <文章目录> --prepare
# 读取两项依赖并在对应阶段写入真实诊断，不代填 PASS。
# 最终 title/body/caption/HTML/evidence 均就绪后：
python <skill目录>/scripts/validate_content.py <文章目录> --bind
# 重新核对锚点、信息保留与承诺兑现，填写 final_read，最后把 status 改为 reviewed。
python <skill目录>/scripts/validate_content.py <文章目录> --json
```

`--prepare` 只新建 pending 记录，拒绝覆盖；允许在正文尚未完成时建表。`--bind` 保留已有诊断，更新五个最终文件的 SHA256，同时重置 status/final_read，要求重新读定稿；它不会通过验收。轻编辑、图注/HTML 或证据改变后都要重新绑定并实际复查。

字段约定（`--prepare` 生成空结构）：

- `planning.skill` / `skill_sha256`：dbs-content 和本次锁定入口哈希。
- `planning.full_picture`：事件全貌；`reader_question`、`added_value`、`structure`：本篇具体策划。
- `planning.coverage[]`：`question`、`finding`、`decision`、`claim_indices`、`reason`。decision 为 included/context/unavailable/irrelevant；前两者引用 evidence.claims 的 **从 0 开始**下标，后两者解释缺口或排除理由。覆盖项由事件决定，不凑数量。
- `review.skill` / `skill_sha256`：dbs-content-value 和锁定入口哈希。
- `review.opening`：`title_quote`、`caption_quote`、`body_quote` 来自当前标题、caption 与正文开头；`expectation`、`readers` 说明继续理由。
- `review.payoffs[]`：`quote` 来自当前正文，`why_it_matters` 具体说明新增理解，`claim_indices` 指向证据。不用“丰富/很好/通过”盖章。
- `review.findings[]`：有问题才列 `problem`、`action`、`result_quote`、`status`；最终必须 resolved。没有发现则空数组，并在 `conclusion` 解释文章怎样兑现承诺。
- `final_read`：轻编辑后的最终信息保留与承诺复核说明；`status` 最后才从 pending 改为 reviewed。

程序会拒绝缺记录、pending、缺必需字段、空洞盖章、失效原文锚点、无效证据引用、未解决问题、依赖哈希不符和定稿后改动。程序不衡量“有趣程度”，不验证判断诚实性；不要写批量批准函数处理真实稿件，也不要把机械 PASS 当用户认可。
