# 逐句审校：强制执行与验收

适用于本入口每一篇新稿及用户明确要求的改稿。开始轻编辑前完整读取本文件；不是写完后挑几句扫禁词。只维护 Skill 时，用离线合成夹具测试，不改现有文章。

## 先分清这次改什么

用户说“句子有 AI 感”时，首先处理句子表达，不擅自重定选题、重搭全文、缩成摘要或重做封面。用户已认可的封面、真实插图与版式保持原样。只有具体结构问题确实需要时，才在必要范围返回主笔；不拿结构调整替代逐句编辑。

`human-writing` 是主笔，`humanizer-zh` 是轻编辑。读取名字、依赖检查、声称“已调用”均不等于完成编辑。读过对应规则后，必须把问题落实为实际改动或有依据的保留。

## 每一句都问，不只审开头

依次读标题、正文（含小标题）、独立 caption、公开图注及图片 alt。审正文时同时看上句和下句，不能脱离语境换词。每句必须说明它在这里完成的具体工作，并检查：

| 问题 | 实际处理 |
|---|---|
| 只宣布“下面要解释什么”，没有开始解释 | 删导读，直接写对象、动作、条件、差异或结果；必要过渡要说清连接哪两件事 |
| 假装发现“容易忽略的细节”，其实只在带读资料 | 直接交代细节及影响；信息值得注意不等于要写“值得注意” |
| 用“有意思、最让人想试、重新定义”等替代具体判断 | 写谁能做什么、哪个约束变了、依据是什么；缺材料就缩短或删掉 |
| 把上一段换词再说一遍 | 删除重复；必要回指须有新的推进，不只换同义词 |
| 抽象名词拥挤、指代不明、搭配或语序拧巴 | 找回明确主语、实际动作和所指对象；读出声检查是否需要倒回去理解 |
| 刻意演“人味”：无根据的我、假亲历、假吐槽、捏造读者误解 | 移除虚构的立场或经历；有依据的作者判断照常保留 |
| 改顺后变强、漏条件、换归因或改变时间状态 | 回到证据恢复限定；不把可能写成已经、演示写成实测、自述写成独立结论 |

本次故障的回归样本（不是要求复用的写法）：

- “这里最让人想试的，是需求可以提到多大”：抽象感受在带读，直接解释支持哪类需求及边界。材料不足，不补更大的承诺。
- “这个区别放进编程任务里就很好理解”：解释尚未发生，直接写任务中的具体差异。不能只换成“换到编程场景就清楚了”。
- “官方模型卡里也有个很容易略过的细节”：直接写披露的事实、测试条件及影响，不先摆出发现细节的姿态。

**不用黑名单代替编辑。** 必要的“不是……而是……”对照、准确引语、代码、网址、数字和术语照常保留。标点、第一人称、长短句没有配额。程序只拦少量已知回归表达，未命中的所有句子仍须语义审校。口水话、碎句或假聊天不算解决。

## 执行闭环

1. 保存原稿或可回退副本。主笔完成后，按上述规则逐句编辑；内部记录真实原句、问题、处理与结果。不为凑问题数量编改动。
2. 按段连读，检查衔接、指代、事实保真、标题与 caption 兑现。不能把整篇变成互不相干的“正确句子”。已流畅且有用的句子保持原样。
3. 最终 HTML、图注和封面完成后，生成待审表：

   ```text
   python <skill目录>/scripts/validate_prose.py <文章目录> --prepare
   ```

   `prose-review.json` 中所有决定均为 `pending`。`PENDING` 及创建文件的退出码 0 只说明待审表创建成功，不是审校通过。已有报告时拒绝覆盖；重审前将旧报告移到内部历史备份，再新建。
4. 对照**当前定稿**逐句填写。严禁用循环、模板、查找替换或测试里的 `synthetic_review` 批量填 `keep`、理由和通读结论。脚本可定位或保存编辑者已作出的不同判断，不可替编辑者编造过程。
5. 发现需改写/删除的句子，先改稿并同步 HTML，不把报告里的 `rewrite/delete` 当成完成。任何文本、图注或 HTML 改动都须重新准备报告并检查当前内容；旧哈希、旧索引不算审过。未变化且仍适用的具体评语可在重新读过后保留，不能盲目复制。
6. 每句和全文通读均完成、所有实际问题已解决，才填顶层 `status: "reviewed"`，然后分别校验：

   ```text
   python <skill目录>/scripts/validate_prose.py <文章目录> --json
   python <skill目录>/scripts/validate_delivery.py <批次目录> --json
   ```

   完整新稿交付包须两者退出码均为 0；仍须实际语义复核、预览与复制测试。只改现有文字、目录中已有三文本及 HTML 而没有 manifest 时，只跑逐句门槛并核对改动范围；不要为总包校验虚构 manifest、来源或封面，结果只称本次文字审校完成。若属于已有批次，用其真实批次目录执行总验收，不把单篇目录误当批次。失败就修对应问题并重验，不能降级版本、删检查项、换旧脚本或编记录获得 PASS。完整交付未完成的条目用 `incomplete`，内部 issues 写具体问题，不称完整交付。

## 字段填写

脚本负责 `schema_version`、四个文件的 SHA256、逐句 `id/field/text/flags`。不要手改绑定字段去适配新稿，改稿后重新准备。

- `units` 覆盖三个文本文件的每个非空单元（句子、标题、无句号行、代码行），以及 HTML 中不与它们相同的文本与 alt。相同的显示句由原文本单元覆盖，同时绑定完整 HTML 哈希。不得合并、漏删、重排或重复单元。
- `decision` 最终只能为 `keep`，意为“当前这句在上下文中可保留”，不是“问题以后再改”。
- `role` 按实际选 `fact / explanation / inference / transition / heading / caption / quote / code / ui`。它记录句子作用，不规定文章结构。
- `anchor` 摘取本句相关短语；`reason` 引用短语，说明提供了什么信息、连接什么或为何此处判断/限定必要。“自然、通过、符合规则”不算理由。不同句子不共用同一条笼统评语。
- `flags` 命中时默认改掉套话。唯一可保留情形：必要原话 `quotation`、代码字面量 `literal_code`、正在讨论这段措辞 `discussed_wording`。`exceptions` 每项写 `rule / basis / protected_text / context / reason`，引语另写内部 `source`。片段须在当前句中以引号/代码标记明确标示。不得为过关把普通叙述补引号或虚构引用；“读起来自然”“读者喜欢”不是例外。未命中时 `exceptions: []`。
- `issues` 记录真实已处理问题：`field / category / before / after / action / reason / status`。`field` 为 `title/body/caption/html_extra`；类别为 `empty_preface/fake_discovery/abstract_judgment/repetition/awkward_syntax/invented_voice/fact_drift/other`。改写用 `rewrite`，删除用 `delete` 且 `after: ""`；落实后才 `status: "resolved"`。没发现问题可为空，不要求每篇有改动。
- `readthrough` 的 `progression / naturalness / factual_fidelity / title_caption` 分别记录推进、表达、事实保真、标题配文兑现。各项填 `decision: "reviewed"`、当前句子 id 的 `anchors` 和引用具体句文的 `note`，说明实际核对结果。一个总 PASS 不代替通读。
- `snapshot_errors` 仅定位准备时的 HTML/文本问题；校验会重新读取文件，删这个字段不会解除失败。

报告是内部过程证据，不放进公开稿、复制区、caption 或对话样稿。内部记录详细，不等于交付一大段编辑过程。

## 程序能证明什么

它阻止缺报告、漏句/重复句、空泛盖章、未处理已知套话、未关闭问题、报告过期、公开文本不同步等可观察失败。不判断所有句子是否自然、不证明新闻真伪，也不验证评语是否诚实；这些依赖实际阅读、对照与编辑。不得宣称“百分之百无 AI 感”，或把 PASS 当成用户已认可个人文风。
